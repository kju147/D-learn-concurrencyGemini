# 教学设计规范（所有课程的写作标准）

> 状态：v1。今后每节课产出后都必须过完这份检查表才能发布。

## 学员画像

一门课同时服务三种人，**靠可跳过的段落**，不是靠三套内容：

- **零基础**：懂 Java 语法，完全没写过线程 —— 名词卡与预备知识的人
- **中级**：做过几个 Spring 项目，背过八股 —— 需要清醒看到每一处机制
- **高级**：技能已有，只想查缺补漏 —— 直接进原理篇/事故复盘篇就跳到结尾测验

## 一节好课的故事线

钩子（事故）→ 剧场演示（动画）→ 预测（先答再看）→ 动手（真 JVM 实验）→ 概念收拢（名词与边界）→ 判题练习（通过证明）→ 复习（卡入 SM-2）

悬置是必要的专业：不是错误示范，是「看完这条你就知道以后不该这么写」。

## 写作手法清单

1. 先掉生活的极佳比，不要上来堆 API 定义。wait/notify 用「外卖能不能送到」，共享资源用「两人抢同一个窗口售票」。学过的程序员会自己补上术语；没有背景的学员会自己等你拿术语。
2. 每节代码长度不超过一屏（15~25 行）。读得下来的代码才会被改变。
3. 任何新名词先让读者预测一个具体结果，哪怕人人都能猜对。
4. 术语第一次出现时给一卡名词解释，之后可以集聚。
5. **动画必须有剧情**（一步一步走的当事件），不要是静态流程图。
6. 一课一夹：约 30 分钟能读完 + 一道判题验收终点。

## 错误范例（进就别进来）

- 「这个 API 的参数是什么意思」式的 API 文档搬运——先丢悬念再丢命名文描。
- 「一改代码就通过」的无伤反例——错误示范必须能在浏览器里真的跑吐。

## 出厂前验收（不达标不发布）

- [ ] 钩子与事故是具体清晰吗？
- [ ] 每个名词第二次出现之前由卡片解释过？
- [ ] 判题练习在浏览器 JVM 里真正能跑通？
- [ ] 名词卡/测验/动画/代码段都放对了位置（不堆在一堆）？
- [ ] 每道题都答得上来「猜到会在哪个细节犯错」？
- [ ] 语言读起来像空调不听使，不是一点气不听？
